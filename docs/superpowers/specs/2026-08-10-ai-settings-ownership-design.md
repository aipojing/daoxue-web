# AI 服务配置归属调整设计

## 背景

当前 `/ai-settings` 同时承载个人 AI 配置和管理员的站点共享配置。普通用户虽然不会看到共享配置区，后端 `/api/admin/settings` 也有管理员权限保护，但页面把两个不同责任放在一起，管理员进入个人 AI 服务时会同时看到全站凭据，信息架构不清晰。

此外，`profile_refine_interval_minutes` 和 `profile_refine_daily_limit` 仍保存在全站 `app_settings` 中。画像提炼实际消耗发起会话账户当前生效的 DeepSeek Key，因此这两个成本控制参数也应归属于账户，而不是站点共享服务。

生产库当前没有显式写入这两个全站设置，运行时使用默认值：提炼间隔 10 分钟、每日上限 0（不限）。生产库目前只有 1 个账户，且 `user_ai_settings` 尚无记录。

## 目标

1. `/ai-settings` 只展示和保存当前登录账户自己的 AI 配置。
2. 管理员的站点共享 AI 凭据和共享兜底开关移至 `/settings`。
3. 画像提炼间隔和每日上限改为账户级设置，跟随发起聊天的账户生效。
4. 保持个人 Key 加密、站点共享权限隔离和视觉服务 SSRF 白名单不变。
5. 迁移后保持当前默认行为，不中断已有聊天、OCR、错题提取、自学处理和画像提炼。

## 非目标

- 不把画像策略细分到学生或学科；同一账户下的所有学生和学科共用该账户的两项策略。
- 不改变每日对话额度 `daily_message_limit` 的管理员管理方式。
- 不删除 `app_settings` 中可能存在的旧画像设置行，以保留旧版本回滚能力；新代码停止读取和写入它们。
- 不改变个人 Key 与站点共享 Key 的解析优先级。
- 不新增第三方视觉服务商或允许普通用户填写自定义视觉接口地址。

## 页面与权限设计

### AI 服务页

所有登录用户都可以进入 `/ai-settings`。页面只包含一个“我的 AI 服务”区域：

- DeepSeek API Key：保存、替换、清除以及当前生效来源。
- 图片识别服务：个人 Key、智谱/阿里云百炼服务商、模型名以及当前生效来源。
- 学科画像提炼间隔：整数，范围 1–1440 分钟，默认 10。
- 学科画像每日提炼上限：整数，范围 0–1000，默认 0；0 表示不限。

管理员和普通用户看到相同的个人配置结构。该页面不请求 `/api/admin/settings`，不展示共享 Key、共享视觉接口、共享模型或共享兜底开关。

保存按钮一次提交个人 Key 草稿、视觉配置和画像策略。Key 输入框继续使用“三态”语义：省略表示不修改、非空字符串表示替换、`null` 表示清除。画像策略始终提交明确的整数值。

### 设置页

普通用户的 `/settings` 继续只展示账户信息和退出登录。

管理员的 `/settings` 在现有邀请码管理和用户管理之前增加“站点共享 AI 服务”卡片，包含：

- 共享 DeepSeek API Key。
- 共享视觉模型 Key。
- 共享视觉接口地址和模型名。
- “允许未配置个人 Key 的用户使用站点共享服务”开关。

该卡片不包含画像提炼间隔或每日上限。前端只在当前用户是管理员时请求 `/api/admin/settings`；后端继续使用管理员中间件保护所有 `/api/admin/*` 路由。

## 数据模型与迁移

新增迁移 `0010_user_profile_refine_settings.sql`，为 `user_ai_settings` 增加两列：

```sql
profile_refine_interval_minutes INTEGER NOT NULL DEFAULT 10
  CHECK (profile_refine_interval_minutes BETWEEN 1 AND 1440)

profile_refine_daily_limit INTEGER NOT NULL DEFAULT 0
  CHECK (profile_refine_daily_limit BETWEEN 0 AND 1000)
```

没有 `user_ai_settings` 行的账户由读取层返回同样的默认值；首次保存任一个人 AI 配置时沿用现有 `INSERT ... ON CONFLICT DO NOTHING` 建行流程，因此无需为所有用户预先创建空记录。

现有个人密文、IV、尾号、视觉服务商和模型字段原样保留。迁移不读取、复制或删除 `app_settings` 中的旧画像设置，因为生产当前没有显式值，默认值完全一致；保留旧值也便于回滚旧代码。

## API 设计

### `GET /api/ai-settings`

现有响应的 `personal` 对象增加：

```ts
profileRefineIntervalMinutes: number;
profileRefineDailyLimit: number;
```

响应仍不包含密文、IV 或完整 Key。没有个人设置行时返回 `10` 和 `0`。

### `PUT /api/ai-settings`

请求增加可选字段：

```ts
profileRefineIntervalMinutes?: number; // 整数 1–1440
profileRefineDailyLimit?: number;       // 整数 0–1000
```

字段通过 Zod 严格校验。保存逻辑只更新请求中出现的字段，并继续使用绑定参数和 D1 batch，避免两个并发局部更新互相覆盖。只有提交新的非空 Key 时才需要加密主密钥；只修改画像策略或清除 Key 不应因主密钥缺失而被保存入口提前拒绝。

### `GET/PUT /api/admin/settings`

响应和请求移除：

- `profileRefineIntervalMinutes`
- `profileRefineDailyLimit`

管理员接口只负责站点共享 AI 凭据、共享视觉配置和共享兜底开关。请求继续由严格字段白名单校验，防止旧客户端通过管理员接口修改已经账户化的画像策略。

## 运行时数据流

`resolveUserAIConfig()` 在解析个人 Key 与共享兜底的同时，从当前用户的 `user_ai_settings` 行读取画像策略；不存在行时使用 10 和 0。返回的账户级配置增加：

```ts
profileRefine: {
  intervalMinutes: number;
  dailyLimit: number;
}
```

聊天路由在每次请求中仍只解析一次账户 AI 配置。成功生成学科回复后，传给 `maybeRefineProfile()` 的是该次请求已经解析出的 `profileRefine`，不再传入全站 `appSettings`。

`maybeRefineProfile()` 的并发租约、最短间隔判断、每日预算预占和失败计费规则保持不变；只把设置来源从全站键值表改为明确的账户参数。每日上限仍按“每个学生、每个学科、每天”统计，但上限数值由该学生所属账户配置。

## 错误与边界处理

- 间隔不是整数或超出 1–1440：返回 400，并提示“画像提炼间隔需为 1–1440 的整数（分钟）”。
- 每日上限不是整数或超出 0–1000：返回 400，并提示“每日提炼上限需为 0–1000 的整数（0 表示不限）”。
- 普通用户访问 `/api/admin/settings`：继续返回 403。
- 个人 Key 密文存在但无法解密：继续 fail closed，不回退到站点共享 Key。
- 个人画像策略列出现不合法历史值：数据库 CHECK 拒绝写入；读取层仍做边界兜底，防御手工数据或未来迁移错误。
- 两个账户可以保存不同策略，彼此不可读取或修改；所有权只从登录会话中的 `user.id` 获取。

## 测试设计

### 迁移测试

- 从 0001–0009 的真实 SQLite schema 应用 0010，确认个人密文和已有行不变。
- 确认新增列默认值为 10 和 0。
- 确认数据库拒绝越界值。
- 确认旧 `app_settings` 画像键仍保留，但新读取路径不依赖它们。

### Worker 与 D1 测试

- 无个人设置行时，`GET /api/ai-settings` 返回 10 和 0。
- 用户 A、B 保存不同画像策略后各自读取正确，数据库行按 `user_id` 隔离。
- 画像提炼使用发起账户的间隔和每日上限，而不是旧全站值。
- 仅修改画像策略不覆盖已有加密 Key、视觉配置或另一个画像字段。
- 非法范围返回 400。
- `/api/admin/settings` 不再返回画像字段，也拒绝提交画像字段。
- 普通用户仍无法访问站点共享设置。

### 前端测试

- AI 服务页的数据模型和保存请求包含个人画像策略。
- AI 服务页不再加载或渲染站点共享配置。
- 管理员设置页渲染站点共享卡片，普通用户不渲染。
- 站点共享保存请求不包含画像策略。
- 输入边界和保存中的按钮禁用状态得到覆盖。

### 完整验证

- 全部 unit 与 Workers/Miniflare D1 测试。
- TypeScript 类型检查和 Vite 生产构建。
- `npm audit` 与 Wrangler dry-run。
- 部署前远程 D1 完整备份，然后应用 0010。
- 生产部署后检查健康端点、迁移状态、管理员设置页和个人 AI 服务页。

## 发布与回滚

发布顺序固定为：代码与迁移测试通过 → 备份远程 D1 → 应用 0010 → 推送并等待 CI → 部署 Worker → 线上验收。

0010 只增加带默认值的列，旧代码会忽略它们；因此数据库先迁移、代码后部署是兼容的。若需要回滚 Worker，旧代码会继续读取保留在 `app_settings` 中的全站画像设置或默认值。回滚期间用户保存的账户级画像策略会保留在新增列中，重新部署新版本后继续生效。

## 验收标准

1. 普通用户和管理员的“AI 服务”页都只展示个人配置和个人画像策略。
2. 站点共享 AI 服务只出现在管理员“设置”页，普通用户前端不可见、接口不可访问。
3. 两个账户可以配置不同画像策略，聊天后各自按自己的策略控制提炼。
4. 共享 Key 的解析、个人 Key 加密和共享兜底开关行为不发生回归。
5. 生产迁移和部署完成后，健康检查通过且无待执行 D1 迁移。
